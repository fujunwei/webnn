### CL-1｜clamp emulation 支持整数输入 ★最低风险起手
- **问题**：`// TODO(crbug.com/422204191): Support more integers because tfl.minimum supports u/int32 and u/int64.`（`:4455`）。当前 `is_emulated` 分支硬编码 `SerializeSubGraphMaxMin<float>(...)`，只对 float 走 min/max 模拟，整数 clamp 无法 emulate。
- **文件**：`tflite/graph_builder_tflite.cc:4455`（`SerializeClamp` 的 `is_emulated` 分支）。
- **工作量**：小。TFLite `tfl.minimum`/`tfl.maximum` 原生支持 u/int32、u/int64，只需按输入 dtype 模板化调用 `SerializeSubGraphMaxMin<T>` 并传对应类型的 min/max 常量。
- **价值**：整数 clamp 在检测框回归（bbox 裁剪）、索引/坐标约束里真实出现；边界极清晰、纯 emulation 补全、无跨文件影响，**适合建立提交节奏的第一枪**。开工前 grep `SerializeSubGraphMaxMin` 看模板是否已支持整数特化即可。

### CL-2｜Conv2D 量化融合缺省 bias 时构造量化空 bias ★贴合量化线
- **问题**：`// TODO(crbug.com/401281047): Construct a quantized empty bias tensor if not provided.`（`:1898`）。`CanFuseQuantizeAndGetOutput(Conv2d)` 当前要求 input/filter/bias **三者都是** DequantizeLinear 输出，只要 `!conv2d.bias_operand_id`（无 bias）就直接 `return std::nullopt` 放弃融合，退回非融合慢路径。
- **文件**：`tflite/graph_builder_tflite.cc:1898`。
- **工作量**：中。需按 filter 的量化参数构造一个全零的量化 bias 张量（zero-point/scale 与融合路径一致），使无 bias 的量化 Conv2D 也能命中融合。
- **价值**：**性能向且贴合你的 QDQ 融合背景**——大量量化 CNN（尤其 depthwise / 无 bias 卷积）当前因缺 bias 而错失融合；LiteRT 默认开启后直接改善线上量化模型延迟。与 07-07 的"Conv2D 激活融合/量化 Gemm 融合"同属融合线但**不同 TODO、不同触发条件**，可连做形成一组融合系列 CL。

### CL-3｜softplus / softsign emulation 常量转 fp16
- **问题**：两处 `// TODO(crbug.com/339654398): Convert the 32-bit floating-point data to 16-bit floating-point data with fp16_ieee_from_fp32_value function if some delegates support 16-bit float inference.`（softplus `:9486`、softsign `:9526`）。emulation 里加的常量 `1` 硬编码为 fp32（`SerializeTensorWithBuffer<float>`），即便 delegate 支持 fp16 也强制升到 fp32。
- **文件**：`tflite/graph_builder_tflite.cc:9486` 与 `:9526`（`SerializeSoftplus` / `SerializeSoftsign`）。
- **工作量**：小-中。按 `input_tensor_info.data_type == FLOAT16` 分支用 `fp16_ieee_from_fp32_value` 生成 fp16 常量；注意 `:9524` 处有 `CHECK_EQ(..., FLOAT32)` 需一并放开。
- **价值**：性能/内存向——fp16 路径省一次隐式提升，减少临时张量字节数（与你的 weights/内存主线呼应）。是下面"创新-3 fp16 端到端"叙事的最小落地单元。

### CL-4｜pool2d 步长/窗口约束归位到 opSupportLimits（前端同步校验）
- **问题**：`// TODO(crbug.com/493988762): Explicitly restrict to int32_t in the WebNN spec or opSupportLimits for synchronous frontend validation.`（`:8042`）。当前步长/filter 超 int32 范围时在**图构建后端**才 `base::unexpected`，是异步失败；应在 `opSupportLimits`/spec 侧做同步前端校验，让 JS 端 `dispatch` 前就能拿到明确错误。
- **文件**：`tflite/graph_builder_tflite.cc:8042`（及 `:8055` 附近 filter 检查）；涉及 `services/webnn/public/cpp` 的 opSupportLimits 暴露。
- **工作量**：小-中。属"验证归位"类，跨 tflite→public/cpp 两层但改动量小。
- **价值**：**spec/开发者体验向**，审阅可见度高于单后端 emulation；把后端才发现的错误前移成同步校验，是 WebNN 一贯推动的方向（与 07-06 的 public/cpp 验证层角度一脉相承，但为全新 TODO）。

### CL-5｜Conv2D（direct / transposed）支持其它张量数据类型

- **工作量**：中（需核对 TFLite CONV_2D/TRANSPOSE_CONV 内核实际支持的 dtype 并放宽 `data_type_limits`，注意 `:4548` 提到的 TFLite 截断转换坑 crbug/384999508）。
- **价值**：扩 Conv2D 数据类型覆盖，减少 fallback；是 int16/量化路径完整度的一环。

### 创新-1｜delegate 感知能力层，系统化收敛 `413083273` 集群 ★与你 renderer 迁移最契合
- **所属层**：架构 / Runtime。
- **活代码证据**：`graph_builder_tflite.cc` 中 **14 处** `// TODO(crbug.com/413083273): Consider the restriction in GPU delegate.`（`:1860,:2043,:2118,:2189,:2226,:2369,:2417,:2469,:2502,:2541,:2590,:2622,:2674,:4200`），集中在各类**量化算子的 Quantize/Dequantize 融合判定**（clamp、gemm、elementwise 等）。典型形态：因 "XNNPack delegate 不支持某量化 kernel" 而**悲观地全局禁用**融合（如 `CanFuseQuantizeAndGetOutput` 的 int8 约束），并未区分当前实际激活的 delegate。
- **为什么现在做**：你刚把 LiteRT CPU 推理从 GPU delegate 迁到 renderer 进程（`5a1917c279`），CPU 路径走 **XNNPACK** delegate，而 GPU 路径是**另一套** delegate（`graph_impl_tflite.cc:394` 的 ChromeML GPU delegate）。这 14 处限制把两条 delegate 的能力差异**耦合硬编码**在图构建里——正是迁移后最该抽象出来的技术债。
- **技术价值**：设计一个 **delegate-capability 抽象**（按 `context_device` / 实际选中的 delegate 查询"是否支持量化 X kernel"），把 14 处散落的悲观禁用改为按能力精确决策——能让 GPU 路径吃到本可用的融合，同时 CPU/XNNPACK 路径保持正确。从"点状修 TODO"升级为"delegate 能力基础设施"。
- **成长价值**：贯通 WebNN→TFLite delegate→XNNPACK/GPU/(未来)OpenVINO NPU 的 capability 模型，正是你后续接 OpenVINO delegate 时**必然要建**的抽象层——一箭双雕。
- **可行性**：中-高。可先抽 1-2 处（如 clamp `:1860`）做 capability 查询 PoC，验证收益后再框架化收敛其余。

### 创新-2｜Android LiteRT GPU/NPU 使能 ★补 OT 最大平台缺口
- **所属层**：平台 / Backend。
- **生态证据（今日新）**：WebNN Origin Trial **明确排除 Android**，因为 Android 上"仅支持 CPU 推理，GPU/NPU 尚不完整"。而 Android 的 WebNN 后端**正是 LiteRT**——这块空白恰好落在你的核心专长上。
- **技术价值**：Android 是 WebNN 触达用户量级最大的平台；打通 LiteRT 在 Android 的 GPU delegate（乃至高通/联发科 NPU delegate）是把 WebNN 从"桌面 demo"推向"移动生产"的关键一跃。与创新-1 的 delegate 能力层天然衔接。
- **成长价值**：从"桌面 LiteRT"扩展到"移动端 GPU/NPU delegate"，覆盖面和履历含金量高；且是 OT 推进的硬阻塞，属于组织级高优先事项。
- **可行性**：中。可先做"Android 上 LiteRT GPU delegate 打通 + 一批代表性模型跑通"的最小里程碑，量化 CPU→GPU 的收益。

### 创新-3｜fp16 端到端推理就绪度（跨 emulation 统一）
- **所属层**：性能 / 内存。
- **证据**：`339654398`（softplus/softsign `:9486/:9526`）、`365168170`（`:1306` fp16 非支持算子插 cast）、以及多处 emulation 硬编码 `<float>` 常量——说明 TFLite 后端的 emulation 路径**尚未系统性支持 fp16**，即便 delegate 能跑 fp16 也被迫升 fp32。
- **技术价值**：建立"emulation fp16 就绪"准则（常量用 `fp16_ieee_from_fp32_value`、临时张量按 delegate 精度选 dtype），系统性降低端侧模型的内存占用与带宽（**直接呼应你的 weights quota / GPU 内存主线**）与延迟。
- **成长价值**：把散落的 fp16 TODO 收敛成一条"精度感知的图构建"叙事，与创新-1 的 delegate 能力层共享同一套"按 delegate 能力决策"的方法论。
- **可行性**：中。渐进第一步即 CL-3（softplus/softsign 两处），再扩到其它 emulation 算子。

### 创新-4｜Origin Trial 阻塞 bug → 数据驱动 CL 选题
- **所属层**：系统 / 质量。
- **动机（今日新）**：WebNN OT 因"M-146 beta 后新报的 release-blocking 问题"**再次推迟**。这些 release-blocker 是**当前组织最高优先级**的、真实用户命中的缺陷——比 grep TODO 更值得投入。
- **技术价值/成长价值**：把任务一从"grep TODO 刷量"升级为"跟踪 OT blocker、认领 LiteRT 相关缺陷"，产出的 CL 可见度和影响力最高，且能深入理解真实模型在 LiteRT 路径的失败模式。
- **可行性**：中。从 crbug 上按 `WebNN` + `Blocking OriginTrial` label 过滤、交叉 LiteRT/tflite 组件认领入手。

### 创新-5｜OpenVINO CiP AOT 编译缓存 + L0 优先级感知
- **所属层**：Backend(NPU) + 系统。
- **生态证据（今日新）**：OpenVINO **2026.2.1** 修复了"NPU plugin 共享 L0 命令队列导致 app/inference 优先级被违反"的问题；litert-intel nightly 已锁 `openvino==2026.2.0.dev`（对应 NPU driver v1.32.1）。
- **技术价值**：在你 OpenVINO delegate 集成方案里，把 compiled-model 的 `export_model`/`import_model` 接上 WebNN 编译缓存，可大幅降 NPU 冷启动 TTFT；叠加 2026.2.1 的 L0 优先级修复，能让交互式 Web 应用的 NPU 推理不被后台任务抢占。
- **成长价值**：横跨 spec 编译缓存 API + 后端产物序列化 + L0/驱动优先级——是你 OpenVINO 主线的自然纵深（区别于 07-01 仅提编译缓存，此处结合了 2026.2.1 的 L0 优先级新维度）。
- **可行性**：中。先在 delegate 内部做 export/import 缓存 PoC 验证 TTFT 收益，再谈 spec 化。
